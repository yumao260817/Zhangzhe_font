## 一、总体评价

项目以「人工拼字 + 管理员审核」为主线，架构清晰（FastAPI + SQLite + Vue3 自研 hash 路由），代码风格统一、可读性好，AGENTS.md 文档质量高。但存在 **2 个阻塞性/严重问题** 与若干安全、健壮性缺陷，**当前状态不建议直接对外发布**。核心风险集中在：依赖缺失导致表单接口不可用、管理员口令泄露到公开仓库、上传与鉴权链路缺乏约束。

## 二、P0 阻塞 / 严重问题

### P0-1 `requirements.txt` 缺失 `python-multipart`，所有表单接口不可用

- **位置**：`requirements.txt`；`src/server/app.py`（register / login / upload_piece / submit / approve / reject 均用 `Form(...)` / `UploadFile`）
- **问题**：FastAPI 的 `Form` 与 `UploadFile` 强依赖 `python-multipart`。实测当前环境未安装该包（`import multipart` 抛 `ModuleNotFoundError`），且 `requirements.txt` 仅列了 11 个包，未包含它。AGENTS.md 第 3 节自己也写明依赖「python-multipart + httpx2(测试用)」，但未写进 `requirements.txt`。
- **影响**：新机器 `pip install -r requirements.txt` 后启动服务，任何带表单的接口一调用即 `RuntimeError: Form data requires "python-multipart"`（500）。注册、登录、上传部件、提交候选、审核全部不可用。**等同于服务无法对外提供功能**。
- **修复**：
  ```text
  # requirements.txt 追加
  python-multipart>=0.0.9
  ```
  若需保留测试能力，再追加 `httpx`（FastAPI TestClient 在新版本已改用 `httpx`，而非 AGENTS.md 所说的 `httpx2`）：
  ```text
  httpx>=0.27
  ```
  并在文档中更新为 `httpx`。

### P0-2 `admin_token=admin123` 硬编码并已提交到公开 GitHub 仓库

- **位置**：`configs/default.yaml:19`（`admin_token: admin123`）；`.gitignore` 未忽略 `configs/`
- **问题**：`configs/` 目录未被 `.gitignore`，`default.yaml` 已入库；remote 为公开仓库。`admin_token` 作为管理员双轨凭证之一（`?token=` 或表单字段），任何人都可用 `?token=admin123` 调用全部管理员接口。git 历史还显示曾有「Remove admin email from default.yaml」提交，说明管理员邮箱也曾入库过。
- **影响**：攻击者可直接：
  - `GET /api/candidates?status=pending&token=admin123` 窥探所有未公开候选；
  - `POST /api/admin/approve|reject` 任意通过/驳回候选，污染字库；
  - `GET /api/candidates/{uid}/project?token=admin123` 下载他人拼字工程文件（含部件布局）。
  等于审核权限完全失守。
- **修复**：
  1. 立即更换 `admin_token` 为高强度随机串，并从 yaml 移除，改由环境变量注入：
     ```python
     # src/server/app.py _admin_token
     import os
     def _admin_token(cfg: dict) -> str:
         return os.environ.get("ZZ_ADMIN_TOKEN") or cfg.get("server",{}).get("admin_token") or ""
     ```
  2. `.gitignore` 增加 `configs/default.yaml`，改提交 `configs/default.example.yaml` 作为模板；
  3. 由于旧 token 已进 git 历史，**仅改文件不够**，需视作泄露处理（轮换所有用该 token 的环境；必要时 `git filter-repo` 清理历史——但公开仓库已被克隆则只能轮换凭证）。

## 三、P1 高危问题

### P1-1 `/api/pieces` 上传部件无鉴权、无大小/频率限制

- **位置**：`src/server/app.py:134-142`（`upload_piece`）；`src/stage_puzzle.py:22-40`（`save_piece`）
- **问题**：接口完全匿名，`file.read()` 一次性读入内存且无大小校验，按 sha256 去重落盘到 `data/puzzle/pieces/`。
- **影响**：可被匿名刷盘（去重只挡相同内容，换内容即可刷）；上传超大文件可 OOM。
- **修复**：
  - 增加登录校验（与 submit 一致）；
  - 限制 `MAX_PIECE_BYTES`（如 2MB），`data = await file.read()` 后校验 `len(data)`；
  - 限制单用户单位时间上传次数（简单的内存计数或按 uid 限流）。

### P1-2 `admin_token` 比较使用 `==` 而非恒定时间比较

- **位置**：`src/server/app.py:33-34`（`_check_admin_token`）
- **问题**：`return token == _admin_token(cfg)`，Python 字符串 `==` 为短路比较，存在时序侧信道。
- **影响**：理论上可逐字节爆破 token（实操难度高，但属标准安全缺陷）。
- **修复**：`return hmac.compare_digest(token or "", _admin_token(cfg))`（`auth.py` 已 `import hmac`，app.py 需补导入）。

### P1-3 `submit` 接口 `author` 字段可伪造

- **位置**：`src/server/app.py:184-214`；`src/stage_puzzle.py:143`（`save_candidate(..., author=author, ...)`）
- **问题**：后端校验了登录态（`user_by_token`），但 `author` 直接取自前端 Form，未与当前登录用户绑定。
- **影响**：登录用户可冒充他人署名，污染候选作者信息，破坏后续署名权/归属。
- **修复**：忽略前端 `author`，强制用登录用户信息：
  ```python
  author = user.get("name") or user.get("email")
  ```
  或以前端值为辅、登录用户为主（如 `author = user.get("name") or user["email"]`）。

### P1-4 `submit` 的 `pieces` JSON 无大小/数量限制

- **位置**：`src/server/app.py:198-205`
- **问题**：`json.loads(pieces)` 无长度上限，`layers` 列表无元素数量上限。
- **影响**：提交超大 JSON 可造成内存占用 / 后端合成（`render_png`/`render_svg`）CPU 占用，DoS。
- **修复**：`if len(pieces) > 512*1024: raise HTTPException(413, ...)`；`if len(layers) > 64: raise ...`。

### P1-5 前端 `png_data` 原样存储，未校验合法性

- **位置**：`src/stage_puzzle.py:151-154`（`png_data is not None` 时直接 `png = png_data`）
- **问题**：当 `png_data` 非空，跳过后端合成，直接 `write_bytes`，未校验是否为合法 PNG、尺寸是否为 512、体积是否合理。
- **影响**：恶意登录用户可上传任意二进制/超大内容污染候选库；审核台 `<img>` 加载异常内容；`cand_png` 返回非图片。
- **修复**：落盘前用 `_imread_bytes(png_data)` 校验可解码，并校验 `img.size == (GRID, GRID)`，体积设上限。

### P1-6 `cand_png` / `cand_svg` 返回前未保证文件存在

- **位置**：`src/server/app.py:317-348`；`src/stage_puzzle.py:222-232`（`cand_files`）
- **问题**：`cand_files` 只判断 `png.exists()` 即返回三元组，svg / proj 可能不存在（人工误删等）；随后 `FileResponse(str(svg))` 会 500。容错弱。
- **修复**：返回前对每个文件 `.exists()` 校验，缺失返回 404 或仅返回存在的部分；更优解见 P2-12（用数据库存的路径）。

### P1-7 审核 `set_status` 未记录操作者与审计日志

- **位置**：`src/stage_puzzle.py:235-244`（`set_status`）；`src/store.py` 的 `review_log` 表
- **问题**：`review_log` 表已建，但 `set_status` 只 `UPDATE candidates`，从不写 `review_log`，也不记录是谁审核的。
- **影响**：审核行为无审计痕迹，出问题无法追责；`reviewer` 参数定义了却从未传入。
- **修复**：`set_status` 内追加 `INSERT INTO review_log (char, action) VALUES (?, ?)`，并把当前管理员 id 一并记录（需扩展 `review_log` schema 加 `reviewer_id`）。

## 四、P2 中危问题

### P2-1 数据库连接无连接池、无统一上下文管理

- **位置**：`src/store.py:55-59`；全项目多处 `conn = store.connect(); ...; conn.close()`
- **问题**：每次请求新建/关闭 SQLite 连接，部分调用未用 `try/finally`（如 `store.connect()` 后异常则不关闭）。
- **修复**：提供上下文管理器 `with store.db() as conn:`，或用 FastAPI 依赖注入 + 连接池（如 `sqlite3` + `check_same_thread=False` 单例，或换 `aiosqlite`/SQLAlchemy）。

### P2-2 `candidates` 表缺索引

- **位置**：`src/store.py:23-35`
- **问题**：`char`、`status` 频繁用于 `WHERE` / `ORDER BY`，无索引；`all_candidates` / `list_candidates` / `gallery` 的子查询随数据增长全表扫描。
- **修复**：`CREATE INDEX IF NOT EXISTS idx_cand_char ON candidates(char);` `CREATE INDEX idx_cand_status ON candidates(status);`（uid 已有 UNIQUE 自带索引）。

### P2-3 `cand_files` 每次遍历全部字目录

- **位置**：`src/stage_puzzle.py:222-232`
- **问题**：按 uid 查文件需遍历 `PUZZLE_CANDIDATES` 下所有字目录直到命中，O(字数)。
- **修复**：`candidates` 表已存 `png_path/svg_path/project_path`，直接用 `SELECT png_path, svg_path, project_path FROM candidates WHERE uid=?` 取路径，O(1)。

### P2-4 `gallery` / `pinyin` 对每个字做文件 `exists()`

- **位置**：`src/server/app.py:292-315`、`262-290`
- **问题**：3755 次 `(PROCESSED / f"{c}.png").exists()` 磁盘 stat，慢。
- **修复**：启动时 `PROCESSED` 一次 `set(p.iterdir())` 缓存，或 DB 化记录 `has_hand`。

### P2-5 `render_svg` 翻转+旋转分支与 PNG 合成可能不一致

- **位置**：`src/stage_puzzle.py:116-126`
- **问题**：`flip` 且 `angle` 同时存在时，`tr` 被整体替换为单元素列表，translate 公式复杂，注释自承「近似一致」。SVG 与实际 PNG（前端 WYSIWYG）可能出现位置偏差。
- **影响**：SVG 仅作辅助展示，主成品走前端 PNG，影响有限，但审核台 SVG 预览可能误导。
- **修复**：统一变换矩阵计算，或 SVG 也直接嵌前端渲染好的 PNG（已有 `png_b64` 叠加层），去掉易错的逐图层 transform 重建。

### P2-6 后端合成 `_compose_rgba` 与前端 `paint.js` 变换顺序不一致

- **位置**：`src/stage_puzzle.py:47-83`（resize→flip→rotate expand）vs `webui/src/utils/paint.js:14-25`（translate→rotate→scaleX）
- **问题**：仅当 `png_data=None`（前端未传 PNG）时后端合成生效，当前前端总传 PNG，故暂不暴露；一旦前端降级或后端重渲染，结果会与预览不符。
- **修复**：统一两侧变换语义；或在后端合成后做一次与前端一致的坐标映射。

### P2-7 `stage_export` 导出 TTF 不含人工拼字成果

- **位置**：`src/stage_export.py:37-87`（仅遍历 `PROCESSED`）
- **问题**：导出只取原始手写图（`data/processed/`），完全不读 `candidates` 表的 approved 候选。AGENTS.md 第 8 节亦列为待办。
- **影响**：人工拼字成果无法进入最终字体，导出的 TTF 仍是 1255 字的原始手写集。
- **修复**：导出时对缺手写的字，取 `candidates` 中 `status='approved'` 的 PNG（前端 WYSIWYG 产物）参与轮廓提取。

### P2-8 字体垂直度量设置异常

- **位置**：`src/stage_export.py:75-76`（`ascent=UPEM, descent=0` / `typoDescender=0`）
- **问题**：`descent=0`、`typoDescender=0` 不合理，基线设置错误，渲染时文字可能溢出行框、行间距异常。
- **修复**：常见取 `ascent=0.8*UPEM`、`descent=-0.2*UPEM`，或按字形实际包围盒计算。

## 五、P3 建议

### P3-1 密码策略过弱
`auth.py:80` 仅 `len>=6`，算术验证码（`10+9`）防不住批量注册。建议提升至 8 位 + 复杂度，或引入图片验证码/限流。

### P3-2 `sessions` 过期记录无清理
过期 session 永留表内。建议加定时清理或登录时顺带 `DELETE FROM sessions WHERE expires_at < datetime('now','localtime')`。

### P3-3 无 `.env` 机制，密钥明文存 yaml
建议 `pydantic-settings` + 环境变量覆盖，敏感配置不入库（配合 P0-2）。

### P3-4 前端 token 存 `localStorage`、图片用 `?token=`
localStorage 易被 XSS 窃取；`?token=` 会进服务端日志/浏览器历史。可接受 trade-off，但建议：关键操作走 Bearer header（已做），图片改用短期签名 URL。

### P3-5 无测试与 CI
项目无 `tests/`、无 CI 配置。AGENTS.md 提及用 TestClient 但无落地。建议补 `tests/` + GitHub Actions（lint=ruff、test=pytest）。

### P3-6 文档与实现漂移
- AGENTS.md 称依赖含 `python-multipart + httpx2`，实际 `requirements.txt` 无；
- AGENTS.md 称 `admin_emails` 配置项，但 `default.yaml` 中该字段已被删（git 历史可见）；
- `cli.py` 只暴露 `init/import/status/stdsrc/preprocess/export/review`，而 AGENTS.md 第 9 节列了更多命令（classify/anchors/components/build_parts/assemble/train/generate/qa/rework），二者不一致。
建议审查后同步文档。
